# HyperCLI ACP Runtime Host Spec

Status: draft

## Purpose

`hypercli-acp` is the first-party runtime host for platform-submitted turns. It
owns the stable platform protocol, runs ACP-compatible agent runtimes such as
OpenCode, and exposes connector adapters for Slack, web, Buzz, and future
surfaces.

The long-term plan is to port the reusable parts of `buzz-acp` into this
package, then retire `buzz-acp` as a separate runtime harness.

## Goals

- Provide one `/ws` protocol for backend automation, web UI, Slack, Buzz, and
  future connectors.
- Make OpenCode the first first-party ACP runtime.
- Keep turn submission transport-neutral: producers submit normalized turns, not
  Slack events or Buzz events.
- Preserve Buzz ACP's hard-won runtime behavior: ACP child lifecycle, session
  affinity, per-conversation queueing, cancellation, steering, reply discipline,
  liveness, and activity capture.
- Inject platform MCP tools into ACP sessions, especially semantic search over
  skills, memory, and workspace context.
- Let connectors deliver replies to their native surface without teaching the
  runtime about Slack, Buzz, or web transport details.

## Non-Goals

- Do not make Slack the core protocol. Slack is a first-party connector, not the
  runtime model.
- Do not duplicate OpenClaw's full Slack UX in the first milestone. Hosted
  relay message ingress, threaded replies, and relay acknowledgements are the
  first surface; assistant threads, approvals, rich Block Kit rendering,
  reactions, and Enterprise Grid edge cases can follow after the core path is
  stable.
- Do not require every connector to expose every capability. Web can start with
  direct text replies; Slack can start with threaded `chat.postMessage`; Buzz can
  keep its existing publish semantics.

## Architecture

```text
platform backend / web / connector
        |
        | HyperCLI ACP WebSocket
        v
hypercli-acp
        |
        | ACP stdio
        v
opencode acp
```

Core modules:

- `protocol`: WebSocket message schema and version negotiation.
- `runtime`: ACP child process lifecycle and runtime presets.
- `queue`: per-conversation pending, in-flight, retry, cancel, and steer state.
- `sessions`: maps `conversation_key` to ACP `sessionId`.
- `prompt`: builds normalized prompt blocks for ACP `session/prompt`.
- `activity`: replayable activity log and live activity stream.
- `connectors`: Slack, web, Buzz, and later additional surfaces.
- `mcp`: platform tool injection, including semantic search.

## Identity Model

`conversation_key` is the stable queue/session key. It replaces Buzz ACP's
channel UUID in core runtime logic.

Examples:

- `web:{workspace_id}:{thread_id}`
- `slack:{team_id}:{channel_id}:{thread_ts}`
- `slack-dm:{team_id}:{user_id}`
- `buzz:{channel_uuid}`
- `automation:{owner_id}:{scheduled_task_id}`

Every submitted turn also carries:

- `turn_id`: generated by `hypercli-acp` unless provided idempotently.
- `request_id`: client-generated id for request/ack correlation.
- `connector`: source and delivery adapter.
- `sender`: user, automation, or system actor.
- `reply_target`: connector-native delivery address.

## WebSocket Protocol

The `/ws` endpoint is bidirectional. Hosted clients authenticate the upgrade
with `Authorization: Bearer ${HYPER_AGENTS_API_KEY}`; after acceptance, all
messages are JSON objects with `type`.

The `/ws` protocol is the platform protocol. It is not ACP. ACP remains the
runtime-child protocol behind `hypercli-acp`.

## Activity Messaging

Activity is a core host feature for every submitted turn, regardless of
connector. Buzz ACP's observer bus is the implementation reference, but activity
must cover web, Slack, Buzz, backend automation, scheduled turns, runtime
lifecycle, ACP child traffic, MCP calls, and delivery attempts.

- Every activity frame has a monotonic process-local sequence number.
- The host keeps a bounded replay buffer for newly connected `/ws` clients.
- New `/ws` activity subscribers receive replay oldest-first, then exactly one
  `activity.replay_end`, then live frames.
- The host subscribes the live sink before replaying persisted activity, then
  flushes the replay boundary, so records emitted during connect are not lost.
- The host can optionally persist a boot-scoped activity log.
- Activity frames are redacted before leaving the process.
- Turn liveness frames are emitted while a turn is active.
- A terminal `turn.completed` or `turn.failed` always closes the turn.

Required activity kinds:

- `runtime.started`
- `runtime.ready`
- `runtime.stopping`
- `runtime.stopped`
- `runtime.error`
- `agent.spawned`
- `agent.exited`
- `agent.restarted`
- `session.created`
- `session.rotated`
- `turn.queued`
- `turn.started`
- `turn.liveness`
- `turn.steer_attempted`
- `turn.cancelled`
- `turn.reply_attempted`
- `turn.reply_delivered`
- `turn.reply_failed`
- `turn.completed`
- `turn.failed`
- `acp.read`
- `acp.write`
- `mcp.tool_call`
- `mcp.tool_result`

The activity bus should not be the durable source of truth for turns. It is a
live/replayable diagnostic stream. The queue/session state is authoritative.

Required turn timing fields:

- `queued_at`: when the host durably accepted the turn.
- `started_at`: when the turn became in-flight. Emit `turn.started` before
  session creation or context fetch so setup stalls are visible.
- `completed_at`: when the turn reached a terminal outcome.
- `duration_ms`: `completed_at - started_at`, measured by the host.
- `queue_duration_ms`: `started_at - queued_at`, when `queued_at` is known.
- `last_liveness_at`: latest liveness timestamp, included on terminal frames
  when available.

Required terminal fields:

- `stop_reason`: runtime stop reason when available, such as `end_turn`,
  `cancelled`, `max_tokens`, `timeout`, or `no_reply`.
- `reply_status`: `not_required`, `not_attempted`, `attempted`, `delivered`,
  `failed`, or `no_reply`.
- `error_class`: `runtime`, `connector`, `platform`, `timeout`, `cancelled`,
  `permission`, or `unknown` on failed turns.
- `usage`: nullable provenance-aware usage payload.

Usage is optional. Adapters should report it only when the child runtime emits
trustworthy usage data. The host must not derive `total_tokens` by summing input
and output tokens. When usage is present, it has this shape:

```json
{
  "source": "_goose/unstable/session/update",
  "delta_reliable": true,
  "model": "gpt-5",
  "turn": {
    "input_tokens": 800,
    "output_tokens": 250,
    "total_tokens": null,
    "cache_read_tokens": null,
    "cache_write_tokens": null,
    "cost_usd": null
  },
  "cumulative": {
    "input_tokens": 1800,
    "output_tokens": 450,
    "total_tokens": null,
    "cache_read_tokens": null,
    "cache_write_tokens": null,
    "cost_usd": null
  }
}
```

`delta_reliable = false` means the per-turn `turn` counts are unknown or
tainted. Cumulative counts may still be useful for display and diagnostics.
Absent provider fields remain `null`; do not collapse absent cache fields into
zero.

## ACP Child Protocol

Runtime adapters talk to child agents over ACP. The initial implementation
should preserve Buzz ACP's strict wire behavior:

- Transport is newline-delimited JSON-RPC 2.0 over child stdio.
- Incoming lines are bounded to prevent unbounded memory growth.
- Host-originated JSON-RPC request IDs are numeric and monotonically assigned
  per child process.
- Responses are matched by `id` and must not carry `method`.
- Notifications have no `id`.
- Unknown agent-originated requests receive JSON-RPC `-32601`.
- `session/cancel` is sent as an ACP notification.
- Cancellation cleanup waits for the original `session/prompt` response within
  a bounded drain window.
- `cancel_drain_timeout` is distinct from `idle_timeout` and hard
  `max_turn_duration` timeout.

Permission requests are runtime-child concerns, not connector events:

- `session/request_permission` is answered according to configured permission
  mode.
- Responses must select the correct option by semantic option `kind`, not by
  assuming stable option IDs.
- If a turn is cancelled while a permission request is pending, answer that
  permission request with `outcome: "cancelled"` before draining the prompt.

## Commands

There are two command classes.

### Platform Commands

Platform commands arrive over `/ws`. They are authenticated and should not be
represented as user chat.

- `turn.cancel`: cancel an in-flight turn and drop its triggering batch.
- `turn.steer`: inject new information into an in-flight turn when supported;
  otherwise fall back to cancel-and-merge.
- `session.rotate`: invalidate the conversation's ACP session; if a turn is
  in-flight, cancel it first.
- `runtime.shutdown`: gracefully stop accepting turns, drain or cancel active
  work according to mode, shut down child processes, then exit.
- `runtime.restart_agent`: replace the ACP child process.
- `runtime.switch_model`: runtime-local model override for future turns.

### Chat Commands

Chat commands are connector-level conveniences and must be gated by connector
policy. They should compile down to platform commands.

Initial reserved commands:

- `!cancel`: owner/admin only; maps to `turn.cancel`.
- `!rotate`: owner/admin only; maps to `session.rotate`.
- `!shutdown`: owner/admin only; maps to `runtime.shutdown`.

Non-owner messages containing these strings are ordinary user messages. This
matches Buzz ACP's behavior and avoids letting arbitrary channel participants
control the runtime.

Chat commands are optional connector sugar. Platform startup, shutdown, scaling,
and scheduled task lifecycle should use platform commands over `/ws`, not chat
messages.

## Queue Semantics

The queue is keyed by `conversation_key`.

Required behavior:

- One in-flight turn per conversation.
- Multiple conversations may run concurrently up to pool capacity.
- New turns while in-flight use a configured policy:
  - `queue`: wait for current turn to finish.
  - `steer`: try non-cancelling steer; fall back to cancel-and-merge.
  - `interrupt`: cancel current turn and re-prompt with replacement framing.
  - `owner-interrupt`: interrupt only when the sender is owner/admin.
- Retry failed batches with bounded exponential backoff.
- Dead-letter batches after repeated failure.
- Preserve session affinity when possible.
- Rotate sessions after explicit `session.rotate`, model switch, hard failure,
  or configured turn count.

## Runtime Adapter: OpenCode First

The first runtime adapter is OpenCode ACP:

```text
command: opencode
args: acp
```

The adapter owns:

- process spawn and shutdown
- ACP initialize negotiation
- `session/new`
- `session/prompt`
- `session/cancel`
- capability detection
- model/env projection
- MCP server injection

Runtime adapters must not contain connector-specific Slack, Buzz, or web logic.

## MCP Injection

Every ACP session should receive platform MCP servers. Initial required tools:

- `skills.search`: semantic search over installed/available skills.
- `memory.search`: semantic search over long-lived user/project memory.
- `memory.write`: durable memory write.
- `context.search`: workspace/project semantic search.
- connector tools such as `slack.reply`, `web.reply`, and `buzz.reply`.

The first implementation can prioritize `skills.search` backed by the platform
embedding model `qwen3-embedding:4b`. Personal memory can be layered in after
turn delivery is reliable.

## Connectors

Connectors normalize inbound transport events to `turn.submit` and deliver
outbound replies.

Connectors are plugin-shaped first-party modules. They are modular and scoped,
but they are not arbitrary dynamic plugins in v1. The host loads a known
connector set from config and gives each connector a narrow `ConnectorHost`
handle.

Core owns:

- `/ws` protocol and authentication.
- durable turn admission, idempotency, and terminal turn records.
- queue policy and per-`conversation_key` locking.
- ACP runtime adapters and session mapping.
- MCP server injection.
- activity emission and redaction.
- platform commands.

Connectors own:

- native event parsing and native auth checks when they receive transport
  directly.
- native relay clients.
- native idempotency key extraction.
- native logical dispatch dedupe.
- native conversation key and reply target construction.
- native history/context fetch.
- native outbound delivery and provider receipts.
- connector-level chat command parsing.

Host-enforced rules:

- Connectors submit `NormalizedTurn` or `NormalizedCommand`; they do not touch
  queue internals, ACP clients, runtime adapters, or session maps directly.
- Runtime adapters never import connector modules or inspect connector-native
  payloads.
- Connector secrets stay in connector config and delivery clients. They are not
  written into prompts, activity payloads, or normalized context.
- All connector tasks are supervised by host lifecycle. Startup, shutdown,
  restart, and health state are visible through activity.
- Connector failures are represented as connector-class activity and terminal
  errors; they must not crash unrelated connectors or conversations.

Conceptual Rust boundary:

```rust
trait Connector {
    fn id(&self) -> &'static str;
    fn capabilities(&self) -> ConnectorCapabilities;

    async fn start(&mut self, host: ConnectorHost) -> Result<()>;
    async fn stop(&mut self) -> Result<()>;
    async fn deliver_reply(&mut self, reply: ConnectorReply) -> Result<DeliveryReceipt>;
}
```

`ConnectorHost` exposes only:

- `submit_turn(NormalizedTurn) -> TurnAccepted`
- `submit_command(NormalizedCommand) -> ControlResult`
- `emit_activity(ActivityFrame)`
- `register_reply_tool(connector_id, tool_schema)`
- `shutdown_signal()`

`ConnectorCapabilities` should declare:

- `inbound`: direct user messages, relay messages, platform automation, or none.
- `outbound`: text, media, blocks, files, reactions, or none.
- `history`: none, thread, dm, channel, or mixed.
- `chat_commands`: whether connector sugar such as `!cancel` is enabled.
- `durable_ingress_required`: whether inbound ack requires durable admission.
- `reply_receipts`: whether provider message IDs are available.

### Web

Web is the simplest connector and should be used to validate the protocol.

- Browser/client submits `turn.submit` directly over `/ws`.
- Replies and activity stream over the same socket.
- `reply_target.kind = "web_thread"`.

### Slack

Slack should live in `hypercli-acp` as a first-party connector.

Rationale:

- Slack is a product surface, not an OpenClaw-specific feature.
- Scheduled turns need the same Slack delivery path as user-submitted turns.
- OpenCode should not know about Slack; it should call connector tools.
- Keeping Slack here lets web, backend automation, and Slack share session,
  activity, queue, and memory behavior.

Slack connector responsibilities:

- Accept already-verified frames from the hosted backend Slack relay.
- Normalize relay `slack_event` frames into `turn.submit`.
- Maintain transport idempotency for Slack `event_id` or relay delivery IDs.
- Deduplicate Slack `message`/`app_mention` twins by logical
  `team/channel/ts`.
- Resolve missing/ambiguous `thread_ts` where feasible.
- Fetch thread or DM history for prompt context.
- Build `conversation_key` from team/channel/thread or team/user DM.
- Deliver replies through the hosted `/slack/api/chat.postMessage` proxy into
  the selected thread.
- Serialize outbound sends per target/thread.
- Keep relay auth outside the ACP runtime prompt and redact it from activity.

Slack relay mode:

- Backend relay receives Slack Events API traffic and verifies Slack signatures.
- The Slack connector connects to the relay as a WebSocket client.
- Relay connection uses `Authorization: Bearer ${HYPER_AGENTS_API_KEY}` plus a
  stable `gateway_id`.
- Required runtime env mirrors the OpenClaw image contract:
  `HYPER_SLACK_APP_ENABLED=1`, `HYPER_AGENTS_API_KEY`,
  `HYPER_SLACK_RELAY_URL`, `HYPER_SLACK_API_URL`, and
  `HYPER_SLACK_GATEWAY_ID`.
- `HYPER_AGENTS_API_KEY` is the relay/platform credential. The connector must
  not require a real Slack bot token; bot tokens live behind the hosted relay.
- Relay frames are bounded; 1 MiB is the initial maximum payload.
- Relay frames carry `hello`, `slack_event`, and `ack`.
- The connector must durably admit the relay frame before sending `ack`.
- If durable admission fails, the connector must not ack; the relay may
  redeliver.
- Relay redelivery must be idempotent by logical Slack message identity when
  available, not only by relay delivery ID.
- Recovered durable relay rows retry until the Slack dispatcher is attached.

Slack idempotency has two layers:

- Transport idempotency: Slack Events API `event_id`, or relay delivery ID when
  no stable Slack message identity exists.
- Logical dispatch dedupe: `message` and `app_mention` events for the same
  Slack post collapse by `team/channel/ts` before visible turn dispatch.

Slack conversation routing:

- DMs use user-scoped conversation keys unless the product later chooses
  assistant-thread semantics.
- Channel and group conversations may be thread-scoped by `thread_ts`.
- A thread reply uses the parent `thread_ts`, not the child message `ts`, for
  conversation and reply routing.
- Missing `thread_ts` may be repaired with `conversations.history`.
- Thread and DM history are connector context. Core receives only
  `conversation_key`, `reply_target`, and normalized history/context.

MVP Slack reply payload:

```json
{
  "text": "message body",
  "unfurl_links": false,
  "unfurl_media": false
}
```

Deferred Slack features:

- Direct Slack Events API receivers or Socket Mode inside `hypercli-acp`
- Assistant thread surfaces
- Block Kit rich rendering
- file upload/download
- reactions and typing/status indicators
- Slack-native approvals
- Enterprise Grid policy matrix

### Buzz

Buzz connector preserves existing `buzz-acp` behavior while the core is being
ported.

- Convert Buzz relay events into `turn.submit`.
- Preserve owner/sibling author gating.
- Preserve `!cancel`, `!rotate`, and `!shutdown` chat command behavior.
- Preserve reply guard until connector reply tools are fully generic.

## Delivery Discipline

The runtime should not rely on freeform assistant text as the only outbound
delivery path. Preferred order:

1. Agent calls a connector reply tool.
2. Host emits `turn.reply` and connector delivers it.
3. If no reply tool was called and `require_reply` is enabled, host sends a
   bounded reply-guard prompt.
4. If still no reply is produced, host completes with `no_reply`.

This mirrors Buzz ACP's reply discipline while making delivery connector
neutral.

## Persistence

`hypercli-acp` writes an agent-turn-level SQLite trace by default at
`.hypercli-acp/trace.sqlite3`. Operators can override the path with `--trace-db`
or `HYPERCLI_ACP_TRACE_DB`.

The trace is for platform visibility, traceback, and future session-memory
materialization. It is not the semantic/vector memory engine. It persists:

- active and rotated session bindings by `conversation_key` and `session_id`
- normalized submitted turns
- terminal turn records with timing, reply status, stop reason, and token usage
  when the runtime reports trustworthy usage
- top-level host activity frames, including queued, started, liveness, reply,
  completed, failed, connector, and lifecycle activity

The trace must not store internal model thinking, raw ACP streams, arbitrary
stdout/stderr dumps, or unbounded tool output. Stored JSON records are bounded;
oversized text is replaced with a bounded prefix plus truncation metadata,
attachments are summarized, and oversized payloads are replaced with truncation
metadata. This protects the PVC and keeps traceback useful even if a turn emits
or reads very large content. Activity rows are retained as a bounded recent
traceback window; turn rows remain the durable agent-turn log.

Query surface:

- `session.list` returns persisted session rows, optionally filtered by
  `conversation_key`.
- `session.trace` returns matching session rows, turns, and activity ordered for
  replay/debugging. It accepts `conversation_key`, `session_id`, and `limit`.
- Trace output is protocol-neutral; web, backend automation, Slack relay, and
  Buzz-originated turns all use the same persisted shapes.

This trace does not by itself make pending or in-flight turns restart-resumable.
Queue recovery requires a separate durable queue/reconciliation pass.

## Porting Plan From Buzz ACP

Phase 1:

- Create `hypercli-acp` package skeleton.
- Copy/adapt ACP client lifecycle.
- Copy/adapt observer/activity bus.
- Define `/ws` protocol and message structs.

Phase 2:

- Replace Buzz `channel_id: Uuid` with `conversation_key: String` in queue and
  session state.
- Introduce transport-neutral `TurnEvent`.
- Keep Buzz connector working through an adapter.

Phase 3:

- Add OpenCode runtime preset.
- Inject platform MCP servers into `session/new`.
- Implement web connector and backend automation submission over `/ws`.

Phase 4:

- Add Slack connector MVP.
- Use OpenClaw Slack behavior as a reference for durable-before-ack, twin
  dedupe, thread repair, session routing, and outbound delivery.

Phase 5:

- Move scheduled-turn submission to `/ws`.
- Retire `buzz-acp` once Buzz connector parity is reached.
