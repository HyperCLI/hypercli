## What the integration does

Stock Buzz Desktop discovers the external `buzz-backend-hypercli` executable;
no custom Desktop build is required. A Desktop-created agent can then run in an
isolated HyperCLI Reef pod instead of on the Mac running Buzz:

1. Buzz creates the agent keypair and owner authorization.
2. Desktop invokes the provider with one JSON request.
3. The provider uses the local HyperCLI credential to create or find a Reef
   deployment.
4. `/usr/local/bin/buzz-acp` connects outbound to the Buzz relay.
5. The selected coding runtime communicates with `buzz-acp` over ACP on stdio.

The human owner's Buzz private key remains in Desktop. The generated agent
private key, owner authorization tag, and merged runtime environment pass
through the provider to HyperCLI.

Supported runtime shapes are OpenCode, Codex, Claude Code, Goose, and Kimi
Code. The current provider requires the HyperCLI `large` tier for Buzz-backed
launches. Ordinary, non-Buzz coding-agent SDK launches retain their normal size
choice.

## Install the provider

Current source builds require Rust 1.95:

```bash
git clone https://github.com/HyperCLI/hypercli.git
cd hypercli
git checkout 0696a2f70137266098de63f3daad26e9125eb5bd

cargo test --workspace --all-features --locked
cargo build --release --locked -p buzz-backend-hypercli

mkdir -p "${HOME}/.local/bin"
install -m 0755 \
  target/release/buzz-backend-hypercli \
  "${HOME}/.local/bin/buzz-backend-hypercli"
```

Confirm the exact executable that Buzz will discover:

```bash
echo '{"op":"info","request_id":"install-check"}' \
  | "${HOME}/.local/bin/buzz-backend-hypercli"
```

The response should contain `"ok":true`, `"name":"HyperCLI"`, and a
`config_schema`.

contains Linux x86-64/ARM64 and macOS Intel/Apple-silicon archives plus

### macOS Gatekeeper

The v0.1.0 macOS artifacts are not signed or notarized. After verifying the
downloaded archive's checksum, run the direct `info` check above. If macOS
blocks it, use **System Settings → Privacy & Security → Open Anyway**, then
confirm the prompt.

Do not disable Gatekeeper globally. Signed and notarized distribution remains
a production requirement.

## Find HyperCLI in Buzz Desktop

Buzz scans its executable directory, its process `PATH`, and
`~/.local/bin` for executable filenames beginning with `buzz-backend-`. The
filename `buzz-backend-hypercli` produces the provider ID `hypercli`.

In Buzz Desktop v0.5.2, **Settings → Agents** is not the creation screen:

1. From **Settings → Agents**, click **Back to app**.
2. Open **Agents** in the main sidebar if it is not already selected.
3. Activate the icon-only plus card with accessible label **New agent**.
4. Click **Create agent**.
5. In the **Create agent** dialog, find **Run on** near the bottom, before
   **Advanced**.
6. Choose `hypercli`. The local option is labelled **This computer**.

**Run on** appears only when Desktop discovers at least one external provider.
Discovery is cached for 30 seconds, and an already-open dialog does not refetch
merely because the cache expires. After installing the helper, close the
dialog, wait at least 30 seconds, and reopen it, or restart Desktop.

Discovery only finds the executable. Selecting `hypercli` then runs its `info`
probe with a 10-second timeout. Gatekeeper, an architecture mismatch, or a
broken binary can therefore make the ID appear while its configuration fails
to load. An identically named executable in the app directory or earlier in
`PATH` can also shadow `~/.local/bin`.

The v0.5.2 source paths for this flow are
`desktop/src/features/settings/ui/SettingsView.tsx`,
`desktop/src/features/agents/ui/UnifiedAgentsSection.tsx`,
`desktop/src/features/agents/ui/AgentDialog.tsx`,
`desktop/src/features/agents/ui/WhereToRunSection.tsx`,
`desktop/src-tauri/src/managed_agents/discovery.rs`, and
`desktop/src-tauri/src/commands/agent_providers.rs`.

## Authenticate HyperCLI

The provider calls the managed-agents HTTP API directly; it does not shell out
to the Python `hyper` CLI. Authenticate the local CLI first, then verify the
account:

```bash
hyper agent login
hyper me
hyper agents list
```

The provider resolves credentials in this order:

1. `HYPER_AGENTS_API_KEY`
2. `HYPER_API_KEY`
3. `HYPERCLI_API_KEY`
4. the same keys in `~/.hypercli/config`
5. the legacy `key` in `~/.hypercli/agent-key.json`

The agents API base uses `AGENTS_API_BASE_URL`, `HYPER_API_BASE`, or
`HYPERCLI_API_URL`. HyperCLI credentials do not belong in the Buzz provider
form: both Buzz and the provider reject secret-looking configuration fields.

## Configure the hosted runtime

Buzz renders the provider's `info.config_schema`. Stock v0.5.2 renders provider
properties as text inputs; it does not turn JSON Schema `enum` values into
select controls. Enter the values exactly.

| Field | Accepted value | Default | Purpose |
| --- | --- | --- | --- |
| `runtime` | `opencode`, `codex`, `claude-code`, `goose`, or `kimi-code` | `opencode` | Runtime/image family |
| `size` | `large` | `large` | Required Buzz coding-agent tier |
| `image` | Trusted image reference | Runtime default | Optional advanced image override |
| `workspace` | HyperCLI workspace ID | Empty | Optional workspace projected under `/home/node/workspaces` |

Default runtime mapping:

| Runtime | Image | ACP child |
| --- | --- | --- |
| OpenCode | `ghcr.io/hypercli/hypercli-opencode:latest` | `opencode acp` |
| Codex | `ghcr.io/hypercli/hypercli-codex:latest` | `codex-acp` |
| Claude Code | `ghcr.io/hypercli/hypercli-claude-code:latest` | `claude-agent-acp` |
| Goose | `ghcr.io/hypercli/hypercli-goose:latest` | `goose acp` |
| Kimi Code | `ghcr.io/hypercli/hypercli-kimi-code:latest` | `kimi acp` |

The provider owns the identity, relay, ACP command, response policy, and timeout
environment. It validates stock Buzz's `turn_timeout_seconds`,
`idle_timeout_seconds`, `max_turn_duration_seconds`, `respond_to`, and
allowlist values before creating the deployment. For Goose, the selected
provider and model are mapped into Goose's runtime environment.

Image overrides receive the generated agent identity and runtime environment.
Use only a trusted immutable image reference.

## Message behavior

Stock Buzz delivers inbound conversation events to the remote `buzz-acp`
harness, but ordinary ACP assistant chunks are activity telemetry—not channel
messages. Non-JSON child output is skipped; there is no plaintext fallback. A
runtime must explicitly invoke the Buzz send command/tool, such as
`buzz messages send`, for the response to appear in chat.

The hosted OpenCode path has connected successfully and explicitly published a
message. That does not mean arbitrary ACP text is automatically forwarded.
The default `RUST_LOG` filter sets `acp::stream=off` to keep generated content
out of centralized container logs. Overriding that filter can expose message
content.

## Lifecycle behavior

Stock Buzz v0.5.2 invokes backend providers for `info` and `deploy` only. It
does not invoke provider stop, undeploy, status, logs, or delete operations.

- Provider-backed agents do not start automatically when Desktop launches.
- Repeating deploy for a running deployment returns the existing deployment ID
  without replacing its launch environment.
- Repeating deploy for a stopped deployment starts it with the current launch
  settings.
- Desktop's Shutdown action sends a best-effort owner-authored,
  agent-mentioned `!shutdown` channel message. It fails without a shared
  channel. New provider launches set `restart: false`; with a backend and
  Lagoon version that support that launch field, an accepted shutdown lets the
  pod terminate, reports the deployment stopped, and releases its slot. Desktop
  still receives no provider acknowledgement and retains its local deployed
  record.
- Existing deployments created before `restart: false` was supported retain
  their saved restart policy. Their `buzz-acp` process may be relaunched by
  Kubernetes after shutdown until the deployment is recreated with the new
  launch shape.
- Desktop Stop and Delete actions do not invoke the provider. A local delete
  can therefore leave remote infrastructure running if shutdown was not
  delivered first.
- Apply launch changes by stopping the deployment through authenticated
  HyperCLI lifecycle tooling, then deploying it again from Buzz.

The provider's `--dry-run` flag is development-only instrumentation, not part
of the stock Buzz protocol. It skips lookup and restart logic and sends one
backend create-validation request with `dry_run: true`; it relies on that API
honoring its non-mutating dry-run contract.

## Ownership modes

### Desktop-owned agents

This is the implemented provider path. Desktop creates the identity and local
managed-agent record, then stores the returned HyperCLI deployment ID. The
agent appears in the local **Agents** view on the Desktop that created it.

Importing the same human owner identity on another Desktop does not reconstruct
that local managed-agent record.

### Hosted, preprovisioned community agents

HyperCLI can separately provision a community, channels, agent identities, and
Reef deployments. Those agents can participate in channels, but stock Desktop
does not adopt them into the user's local **Agents** inventory. HyperCLI remains
their lifecycle authority. Remote discovery/adoption requires a future upstream
provider contract.

## Test boundaries

Current automated coverage includes:

- native Rust workspace and one-shot provider protocol tests;
- exact sanitized stock `info` and `deploy` request/response fixtures;
- a five-runtime dry-run matrix of representative generated request shapes;
- five deployed image/runtime sanity gates;
- OpenCode and Goose inference/tool-use coverage;
- a provider → HyperCLI → Lagoon deployment smoke using a dedicated Pro test
  identity and a full-SHA-tagged OpenCode candidate.

The backend workflow pins the provider source through `HYPERCLI_REF` and builds
the root Cargo workspace. The provider smoke checks deployment, environment,
workspace ownership, passwordless sudo, and idempotent retry.

It handcrafts the provider request; it does not start the official Buzz Desktop
binary, send a relay prompt, or prove a Desktop-visible tool response. A real
Desktop → relay → `buzz-acp` → runtime → explicit send-tool E2E remains a
production acceptance requirement.

## Security boundaries

The provider receives the agent nsec and merged runtime environment and sends
them as raw deployment environment values. The backend currently persists
those values in `Agent.launch_config`; authenticated deployment reads,
environment access, or exec access may expose them.

Additional preview limitations:

- unsigned and unnotarized provider distribution;
- mutable default `latest` image references;
- broad development credential rather than a narrow deploy-only capability;
- passwordless sudo in coding images;
- unrestricted runtime egress;
- automatic ACP permission approval;
- no stock-provider lifecycle callback for remote shutdown or cleanup.

Production requires encrypted or external launch-secret references, redacted
read APIs, restricted env/exec access, narrow and revocable credentials,
immutable promoted images, signed/notarized binaries, and orphan/lifecycle
reconciliation.
